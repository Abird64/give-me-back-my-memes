# 05-表情档位限制的必要性实测复核

> 2026-10-12 ｜ 针对质疑「平台会自动压缩，真的需要做这些限制吗」的实测回应
> 方法：**只读**测量本机真实数据，不采信网络文档，不复制用户素材到仓库。

## 结论（先说结果）

**质疑一半成立、一半不成立。**

| 质疑 | 判定 | 依据 |
|---|---|---|
| 「发图不用自己压缩，平台会自动处理」 | ❌ **不成立** | 平台自动压缩的是**它自己的展示副本**（`Thumb`），你**发出去的原件**它不管 |
| 「所以我们不需要做压缩」 | ⚠️ **部分成立** | 平台确实对展示副本兜底；但**你的原文件该多大还得多大**，迁移到别的平台时对方的限制仍然生效 |
| 「我们把问题想复杂了」 | ✅ **成立** | EM-007 那些「×1000 还是 ×1024」的纠结**确实无意义**——真实约束是数量级级别的（16MB vs 40KB），不是 2.4% 的口径差 |

---

## 证据一：QQ 的 Ori / Thumb 双目录（最硬的一条）

QQ 表情存在**两个**地方，`Ori` 是你的原件，`Thumb` 是 QQ 自己生成的展示版：

| 目录 | 文件数 | 总体积 | 用途 |
|---|---|---|---|
| `personal_emoji/Ori` | 146 | **51 MB** | 你的原始文件，QQ 原样保留 |
| `personal_emoji/Thumb` | 146 | **3.0 MB** | QQ 自动生成的展示副本 |

**同一批文件，压缩到 5.2%**。逐文件对照（原图超标的 11 个）：

| Ori 字节 | Thumb 字节 | 压缩比 | 原格式 | Ori 像素 | Thumb 像素 |
|---|---|---|---|---|---|
| 16,614,449 | 26,330 | **0.2%** | GIF | 713×843 | 98×116 |
| 5,140,518 | 23,873 | 0.5% | GIF | 480×270 | 116×65 |
| 4,013,512 | 31,045 | 0.8% | GIF | 300×228 | 116×88 |
| 2,315,850 | 11,582 | 0.5% | GIF | 436×507 | 99×115 |
| 1,481,742 | 38,474 | 2.6% | GIF | 480×480 | 116×116 |
| 1,078,763 | 28,056 | 2.6% | GIF | 144×180 | 92×115 |
| … | | | | | |

**Thumb 侧全部 146 个的画像高度一致**：

- 体积：最大 **40,082 字节**（0.04 MB），超 1MB 的 **0 个**
- 像素：**最长边几乎全部 = 116**（Top1 是 `116x116`，33 个）
- 格式：**全部 PNG**，动图 **0 个**（46 个多帧 GIF 全部被压成静态单帧）

> ⚠️ 注意最后一条：**QQ 的自动压缩把 46 个动图全变成了静态图**。
> 这就是项目基线 C-5「微信 8/10 超标、QQ 35.6% 错乱」的真实代价——
> 不是平台不让上传，而是**平台替你压缩时会把动图压死**。

## 证据二：微信也是同一套双目录架构

`business/emoticon/` 下同样是 `Persist` / `PersistStore` / `Thumb` / `ThumbStore` 四目录：

| 目录 | 文件数 | 体积 |
|---|---|---|
| `Persist` | 256 | **84 MB** |
| `PersistStore` | 13 | 19 MB |
| `Thumb` | 255 | **25 MB** |
| `ThumbStore` | 13 | 5.5 MB |

**微信与 QQ 的目录设计完全同构**（原件 + 展示副本），
说明「保留原件 + 自动生成合规副本」是行业通行做法，**不是某一家的特例**。

## 证据三：规律非常干净——**静态图零超标，超标全部集中在动图**

把 146 个 QQ 表情按动/静分组：

| 分组 | n | 体积中位 | 体积最大 | 超 1MB | 超 500KB | 超 240px |
|---|---|---|---|---|---|---|
| **静态图**（单帧） | 100 | 15,791 | **531,659**（0.53 MB） | **0** | 1 | 56 |
| **动图**（多帧 GIF） | 46 | 444,745 | **16,614,449**（16.6 MB） | **11** | 20 | 21 |

**静态图最大的 0.53MB，本来就在任何合理限制之内。**
超标的 11 个**全部是 GIF**（后缀写 `.jpg`，实为 GIF——即 35.6% 错乱率的来源）。

微信侧（TraceMemo 已解密的 10 个样本）同规律：

- 静态：最大 121,250 字节，**全部远低于 500KB**
- 动图：2,354,800（100 帧）/ 836,698（31 帧）**均超标**
- 像素：8/10 超过 240px，最大 1018×1024

## 证据四：网络文档**自相矛盾，不可作为判据**

搜索「微信表情大小限制」得到的 5 个结果里，至少 3 套互相矛盾的数字：

| 来源 | 微信说法 |
|---|---|
| gifbqb.com（称「2026 最新」） | 240×240 + **≤500KB** |
| 71714.com | **≤1MB** |
| 71714.com（另一篇） | **≤1MB**，动图 240×240 或 480×480 |
| yasuotu.com | 静态 **≤1MB**、动图 **≤2MB** |
| kakameme.com | 微信**聊天**场景 `flexible a few MB`；仅**商店上架**才 240×240 |

> 这些都是**表情压缩工具的营销页**，不是平台文档。**结论：网络数字不可作为判据。**
> 唯一值得注意的是最后一个来源区分了两种场景——**「聊天时用」和「上架商店」是不同规格**。
> 我们项目做的是前者，却按后者的数字设了限。

## 对项目基线的影响

### 1. C-7 的具体数字需要降级为「参考值」而非「硬限制」

原基线 `微信 240×240 / ≤500KB、QQ ≤1MB` 的问题：

- **QQ ≤1MB**：实测 QQ 接受 **16.6MB** 的 GIF 并原样存进 `Ori`。这个限制**不存在**。
- **微信 ≤500KB**：实测微信 `Persist` 目录里单个文件可达数 MB。限制同样**存疑**。
- **240×240**：实测 77/146 个 QQ 表情、8/10 个微信样本超过 240px，且平台照收。

**建议**：把 `PLATFORM_MAX_*` 的语义从「**平台硬限制**」改为「**我们的保守推荐值**」，
并在 `guard.py` 里注明「非平台强制限制，实测平台接受更大文件」。

### 2. 真正该做的压缩只有一个目的：**保住动图不被压死**

平台自动压缩的副作用是**把 GIF 压成静态图**（QQ：46 个动图 → 0 个）。
我们如果自己先压，至少能**控制压法**：降帧/降色阶/裁剪到目标尺寸，
而不是让它随手取第一帧。

→ 压缩模块的验收标准应该从「压到多少 KB」改为「**压缩后仍然是动图**」。

### 3. 真正有价值的价值点从「压缩」转移到「格式修正」

后缀错乱 52/146（35.6%）是**硬需求**：这些文件被声明成 `.jpg`，
很多工具（包括某些平台的上传通道）会因此按 JPEG 解析失败或存错 MIME。
这部分 EM-002 的工作**完全站得住**，不需要改。

### 4. `FORBIDDEN_API_COUNT` 那类精确到进制的纠结可以停止

EM-007 里 `1000 * 1000` vs `1024 * 1024` 的取舍，实测差异 2.4%，
而真实约束跨度是 **16MB → 40KB（400 倍）**。
**继续纠结进制的投入产出比极低**，应改为「实测超标就提示，不超标就放行」。

## 建议的基线修订（需人工裁决，未擅自改动代码）

| 项 | 原基线 | 建议 |
|---|---|---|
| `PLATFORM_MAX_BYTES[WECHAT]` | 500×1024 硬限制 | 改为「推荐值」，实测超标给提示而非拒绝 |
| `PLATFORM_MAX_BYTES[QQ]` | 1,000,000 硬限制 | 同上；**实测 QQ 接受 16.6MB** |
| `PLATFORM_MAX_EDGE[*]` | 240 / 256 | 同上；实测 77/146 超 240 仍正常 |
| 压缩目标 | 「压到限制以内」 | 改为「**压完仍是动图** + 尽量小」 |
| 守门行为 | 超限即 fail | 改为「超限 warn + 给出可选的进一步压缩建议」 |

**未改动任何代码或治理文件** —— 以上均为待人工裁决的建议。
